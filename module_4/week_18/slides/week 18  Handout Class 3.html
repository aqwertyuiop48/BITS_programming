PART A: PERFORMANCE AND SCALABILITY TESTING 

1. Why Performance is a Quality Dimension 

Until now, most of our testing was about correctness and reliability. But in production, another question becomes equally important: Can the system handle real-world load?

A correct model that responds too slowly is still a failure. 

Performance testing and scalability testing are two distinct but related disciplines:

  • Performance testing measures how e ciently the system serves predictions — speed and resource usage.
  • Scalability testing measures how well the system handles increasing demand — growth and load handling.

In production AI systems, both are non-negotiable. Speed is part of correctness. 

2. Inference Latency 

Inference latency is the time taken for a model to generate a prediction — from receiving input to returning output. 

Why a single average is not enough:

Metric   

Definition  

Why It Matters 
  Mean Latency Average time across all requests Useful overview, but hides tail behavior
P50 (Median)   50% of requests complete      within this time    Typical user experience
P95 95% of requests complete within this time   Near-worst-case experience 
P99 99% of requests complete within this time SLA boundary — what you guarantee
Worst Case Maximum observed latency Reveals extreme outliers

Critical insight: Users experience delays, not averages. A system with a mean latency of 40ms might have a P99 of 500ms — meaning 1 in 100 requests takes 500ms. That 1% matters.

Production SLAs are de ned at P99, not at the mean.

Why Warmup Matters 

The rst few inferences after a model loads are slower due to memory allocation and kernel compilation. Always discard warmup runs before measuring latency. Measurements taken without warmup in ate latency numbers and misrepresent steady-state performance. 

3. CPU vs GPU Performance 

The same model behaves very differently depending on the hardware it runs on. 

Hardware    

Strength   

Typical Use Case 
  GPU Massively parallel — thousands of operations simultaneously Server-side high-throughput inference
CPU   Sequential, general-purpose    Edge devices, low-volume workloads 

Example impact: a CNN that runs in 15ms on GPU may take 120ms on CPU — an 8× difference. This has direct implications for deployment. 

Key principle: You cannot assume lab performance equals production performance. Performance testing must evaluate the target hardware. A model benchmarked on a GPU workstation and deployed to a CPU edge device will behave completely differently.

4. The Latency-Throughput Tradeoff 

Batch size — the number of inputs processed at once — creates a fundamental tradeoff between latency and throughput. 

Mode 

Batch Size 

Effect on Latency 

Effect on Throughput 
  Real-time serving 1 Low per-request latency Lower throughput (GPU underutilized)
Batch inference   16–32    Higher per-batch    latency    Much higher throughput 

Illustrated tradeoff:

Batch Size 1 → latency: 40ms → throughput: 25 img/s 

Batch Size 8 → latency: 160ms → throughput: 50 img/s

Batch Size 32 → latency: 550ms → throughput: 58 img/s

Throughput increases with batch size because hardware parallelism is better utilized. But the time any individual user waits also increases.

Optimising throughput can hurt latency.

The right choice depends on the use case: 

  • Real-time system (e.g., autonomous driving): minimize latency, even at the cost of throughput
  • Batch processing (e.g., processing stored video o ine): maximize throughput 

5. Scalability Testing

Scalability testing simulates high traffic to understand how the system behaves under load. 

What to measure under load:

Metric  

What It Reveals 
  Response time under concurrent requests  Does latency grow gracefully or spike suddenly?
Failure rate at high RPS (requests/second)   At what load does the system start rejecting requests? 
Memory usage under sustained load   Are there memory leaks? Does usage grow           unboundedly? 
CPU / GPU utilization  Is the hardware e ciently used?
Queue depth   Are requests backing up faster than they are processed?

Common failure modes that only appear under load:

  • Memory leaks — memory usage grows over time and eventually crashes the process
  • Thread contention — multiple threads compete for shared resources, causing blocking
  • Queue saturation — requests arrive faster than they are processed, causing them to pile up

These issues do not appear during single-request testing. Systems often fail under load, not under correctness tests. This is why scalability testing is a separate discipline, not a subset of API testing. 

6. Model Quantisation

Quantisation is a model optimization technique that reduces the numerical precision of model weights. 

How it works: 

  • Standard models use FP32 (32-bit oating point) — 4 bytes per weight
  • Quantized models use INT8 (8-bit integer) — 1 byte per weight
  • Result: up to 4× reduction in model size, and faster arithmetic on supported hardware 

Types of quantisation:

Type  

 When Applied 

 Requires Retraining? 

Notes 
 Dynamic             Quantisation  Post-training, at inference time  No  Only quantizes fully-connected layers; minimal impact on conv layers
Static Quantisation   Post-training, with    calibration data   No (but needs     calibration)   Full network quantization; requires     representative data 
Quantisation Aware Training (QAT)  During training   Yes    Best accuracy preservation; most complex

The Performance-accuracy Tradeoff:

 Full FP32 ← maximum accuracy 
      Dynamic Quant ──────── slight accuracy delta 
      Static Quant  ─────── moderate accuracy delta, faster 
Pruned + Quant ─────────── significant compression, measurable delta 
Speed / Size →

You cannot blindly optimise. Every quantization decision must be validated:

  1. Benchmark performance before quantization
  2. Apply quantisation
  3. Benchmark performance after quantisation
  4. Compare accuracy between original and quantized model
  5. Accept the tradeoff only if the accuracy delta is within acceptable bounds 

Optimization is always a balance between speed and accuracy.

PART B: AI SECURITY THREATS 

1. Why AI Security is Different 

Traditional software security focuses on code vulnerabilities — SQL injection, buffer over ows, authentication bypass. These threats apply to AI systems too.

But AI systems have additional vulnerabilities that are unique to the model itself.

The Three Levels of AI Attack Surface:

Level 

What Can Be Attacked 

Example 
 Input Level  The data sent to the model  Adversarial examples that fool classi   cation 
 Model Level   The model's learned   knowledge   Model inversion to extract training data 
 API Level  The interface between model and world  DoS attacks, unauthorized access 

A system that is accurate and fast but insecure is not production-ready. Security is not an add-on. It is part of quality.

2. Adversarial Attacks (Security Perspective) 

In Class 1, we studied adversarial attacks from a quality perspective — measuring robustness. Now we consider them from a security perspective — understanding how attackers exploit them. 

An adversarial attack involves intentionally modifying an input by a tiny, carefully calculated amount to cause the model to misclassify it. The modi cation is typically invisible to humans but catastrophic to the model.

Security Implications:

  • A stop sign sticker crafted to fool an autonomous vehicle's vision system 
  • An X-ray image minimally altered to bypass a medical screening model 
  • An ID photo perturbed to fool a face recognition access control system 

If you can fool your own model easily, someone else can too. Adversarial testing is therefore not only a robustness concern — it is a defense concern. 

Why FGSM is Important to Understand:

FGSM (Fast Gradient Sign Method) uses the model's own learned gradients to craft the most damaging perturbation. This means: 

  • The attacker needs only black-box query access to the API
  • The model's own knowledge is used against it
  • Even tiny epsilon values (ε = 0.01) can collapse accuracy

Defenses against adversarial attacks:

Defense 

Method  

Trade-off  
 Adversarial Training   Include adversarial examples   during model training   Slower training, higher cost, more robust   model 
 Input Preprocessing   Apply smoothing or   compression before inference   May slightly reduce accuracy on clean   inputs 
 Certi ed Defenses   Randomised smoothing with   provable bounds   Complex, slower inference 
 Anomaly Detection   Flag statistically unusual inputs   before inference   May reject valid edge-case inputs 
 Confidence Thresholding   Reject predictions with con   dence below a threshold   Reduces availability but increases   reliability 

3. Model Inversion Attacks 

Model inversion is an attack in which someone attempts to reconstruct sensitive training data by repeatedly querying the model and analyzing its outputs. 

How it works:

  1. An attacker sends many queries to the prediction API 
  2. Each response includes con dence scores and class probabilities 
  3. By analysing patterns in these outputs, the attacker can infer statistical properties of the training data 
  4. In some cases, they can reconstruct approximate versions of training samples 

Why this matters: A model can reveal information you never intended to share. Even if the training dataset is private, the model's outputs can leak it.

Example: A medical image classi er trained on patient data could leak information about the patients — not through a data breach, but through its own prediction behaviour.

Mitigations:

  • Limit the information returned in API responses (e.g., return top-1 class only, not full probability distribution) 
  • Add noise to output probabilities 
  • Rate limit queries per client to prevent systematic probing 
  • Monitor for unusual query patterns 

4. API Abuse and Denial-of-Service

When a model is exposed as a public API, it becomes a target for abuse:

Description   

Impact

Large payload attacks   Extremely large images sent repeatedly  Memory exhaustion, server crash 
Model extraction Systematic queries to reconstruct model behavior   Intellectual property theft

AI inference is computationally expensive. A single forward pass through a deep CNN consumes meaningful CPU/GPU time. Without protection, an API is trivially overwhelmed.

Exposure without limits invites abuse.

5. Authentication: JWT

Authentication is the process of verifying that a caller is who they claim to be. 

JSON Web Token (JWT) is a widely used stateless authentication mechanism for APIs

How JWT works:

Step 1: Client sends username + password to /token endpoint&nbsp;

Step 2: Server verifies credentials against user database&nbsp;

Step 3: Server issues a signed JWT token&nbsp;

Step 4: Client attaches token to every subsequent request&nbsp;

&nbsp; → Authorization: Bearer 

Step 5: Server verifies token signature on each request&nbsp;

Step 6: If valid → process request; if invalid → HTTP 401 Unauthorised&nbsp;

JWT structure

A JWT token consists of three base64-encoded parts separated by dots:

eyJhbGci...  .  eyJzdWIi...  .  Zm9vYmFy... 
   Header         Payload       Signature

  • Header: Speci es the signing algorithm (e.g., HS256)
  • Payload: Contains claims — username, expiry time, issued-at
  • Signature: HMAC of header + payload using a secret key

Why JWT is used: It is stateless — the server does not need to store session data. The token itself contains all necessary information and can be veri ed using the secret key.

Key security rules for JWT:

  • The secret key must never be committed to source code — always loaded from environment variables 
  • Tokens must have an expiry ( exp claim) — typically 15–60 minutes 
  • Tokens should be transmitted only over HTTPS — never over plain HTTP 

Without authentication, anyone who can reach the API can probe the model, extract predictions, and potentially mount model inversion attacks. 

Security begins with controlled access. 

6. Rate Limiting 

Rate limiting controls how many requests a client can make within a time window. 

Sliding Window Algorithm:

Window: [t-60s ──────────────────────────── now] 
Request 1: Allowed (count = 1) 
Request 2: Allowed (count = 2) 
... 
Request N: Allowed (count = N) 
Request N+1: BLOCKED → HTTP 429 Too Many Requests

At each incoming request:

  • Remove all timestamps older than the window from the client's history 
  • Count remaining timestamps 
  • If count ≥ max_requests → return 429 
  • Otherwise → add timestamp, process request 

Rate Limiting Serves Multiple Security Purposes:

  • Prevents DoS from request ooding
  • Prevents model extraction attacks (too many queries required)
  • Prevents brute-force attacks on authentication
  • Protects all users from being affected by one bad actor  

In distributed systems: An in-memory rate limiter only works for a single server instance. In production with multiple API replicas, rate limiting state must be stored in a shared system (e.g., Redis) so all instances enforce the same limits.

PART C: AUTOMATED AND CONTINUOUS TESTING 

1. Why Manual Testing Does Not Scale 

After you benchmark performance once and harden the API once, what happens next month? After the next model update? After a dependency upgrade? After a hardware change? 

If your tests are not automated, regressions are guaranteed.

Consider a realistic scenario: a model originally had 92% accuracy and 40ms latency. After optimisation and refactoring, accuracy drops to 88% and latency increases to 70ms. The API still returns 200. Nothing crashes. Without automated checks, this degradation enters production undetected. 

The difference between manual and automated testing:

Without Automation  

With Automation 
  Testing depends on memory  Testing depends on systems
Security depends on discipline   Security depends on pipelines
Performance depends on periodic review Performance depends on enforced thresholds
Quality is hoped for Quality is verified

Automation transforms testing from a manual activity into a system-level guardrail.

2. Regression Testing for ML Systems

Regression testing in software engineering checks whether new changes break existing functionality. 

In ML systems, regression testing is different — models are probabilistic, so you cannot assert exact outputs. Instead:

Traditional software regression:

assert predict("input_A") == "expected_output_X" # exact equality 

assert predict("input_A") == "expected_output_X"  # exact equality

ML regression testing: 

assert accuracy_on_test_set >= ACCURACY_THRESHOLD  # bounded behavior 
assert p99_latency <= SLA_THRESHOLD                 # bounded behavior 
assert api_response.status_code == 200              # exact (for HTTP cod

ML testing is threshold-based, not equality-based.

What ML regression tests must cover: 

Test Category  

What Is Checked 

Pass Condition   
 API Correctness   HTTP status codes, response fields, error handling All codes match expectations
Accuracy Gate  Model accuracy on validation/test set   Accuracy ≥ minimum threshold
Latency Gate P99 latency across N requests   P99 ≤ SLA threshold
Security Gate Unauthenticated requests rejected HTTP 401 returned without token
Schema Consistency Response elds and types All required elds present, correct types
Determinism Same input → same output Predictions consistent across N runs

3. The ML Testing Pyramid 

           ┌──────────────────────┐ 
           │   End-to-End Tests   │  Slow, few — full workflow 
           ├──────────────────────┤ 
           │  Integration Tests   │  Multi-component — canary, metrics 
           ├──────────────────────┤ 
           │  API Response Tests  │  Fast, many — endpoint correctness 
           ├──────────────────────┤ 
           │  Accuracy Gate Tests │  Model quality — threshold checks 
           ├──────────────────────┤ 
           │  Latency Gate Tests  │  Performance SLA — threshold checks 
           └──────────────────────┘

Base of pyramid = run most often, fail fast. Latency and accuracy threshold tests are cheap to run and provide immediate signal. End-to-end tests are slower and run less frequently. 

4. Writing Automated Tests with pytest

pytest is the standard Python testing framework. It auto-discovers test les and functions by naming convention.

Naming Conventions:

Test les: test_*.py or *_test.py
Test functions: test_*
Test classes: Test*

The Arrange-Act-Assert (AAA) pattern:

def test_predict_returns_200_for_valid_image(): 
# Arrange — set up the test input 
    image = create_test_image(size=(128, 128)) 
# Act — perform the operation 
    response = client.post("/predict", files={"file": image}) 
# Assert — verify the outcome 
assert response.status_code == 200

Best Practices:

Practice 

Description 
  One assertion per test Each test verifies exactly one behaviour — easier to diagnose failures
Descriptive names   test_corrupt_image_returns_400 not test_error
Use fixtures @pytest.fixture for reusable setup — test images, auth tokens, DB state 
Test edge cases Empty les, corrupt data, boundary values, missing elds
Avoid test interdependence  Each test must pass independently of others

5. Quality Gates and Thresholds

A quality gate is a minimum passing criterion that must be satis ed before code can proceed to the next stage (e.g., merge to main, deploy to production). 

Example quality gates for an ML system:

# Accuracy gate 
assert model_accuracy >= 70.0  # "Fail the build if accuracy drops below 

# Latency gate 
assert p99_latency_ms <= 200  # "Fail the build if P99 exceeds 200ms" 

# Security gate 
assert unauthenticated_response.status_code == 401  # "Fail if auth is br

Why thresholds instead of exact values: Model outputs are non-deterministic in a statistical sense — slight changes in preprocessing or hardware can change the 4th decimal place. Thresholds accommodate this natural variation while enforcing meaningful constraints. 

Setting the right thresholds:

Continuous Integration (CI) is the practice of automatically validating every code change by running the full test suite.

In ML systems, CI must validate more than just code correctness:

The key shift in mindset:

Instead of "we expect latency to be low," you say "fail the build if latency exceeds 50ms."

Automation enforces expectations. Without it, they are just hopes.

PART D: FAIRNESS AND COMPLIANCE

1. Beyond Technical Quality 

So far, quality meant: generalisation, robustness, system stability, performance, and security. 

In Class 3, we expand this definition further. Quality also means: 

  • Equitable performance — the model works consistently for all user groups
  • Responsible deployment — the model does not cause unintended harm
  • Regulatory awareness — the model complies with applicable laws
  • Ethical consideration — the model is evaluated for societal impact

Production AI systems interact with real people. That interaction creates responsibility.

2. What is Fairness in AI? 

Fairness in AI means ensuring that a model does not systematically disadvantage certain groups, categories, or demographic subgroups. 

A model can be accurate overall and still be unfair.

Example: An image classi cation model achieves 90% overall accuracy. But for one subgroup — defined by lighting conditions, sensor type, or demographic characteristics — accuracy drops to 60%. If you only report global accuracy, you miss this completely.

The aggregate metric hides the disparity. Bias hides inside averages.

Manifestations of unfairness in AI systems: 

  • Face recognition performing better on lighter skin tones than darker ones 
  • Defect detection performing well on one product batch but failing on another 
  • Medical classi ers performing well on one demographic but poorly on another 
  • Loan approval models denying credit to certain groups disproportionately 

These are not purely accuracy problems. They are fairness problems — with real-world consequences for real people. 

3. Subgroup Analysis

Subgroup analysis is the practice of measuring model performance separately across different groups or conditions, rather than only globally. 

What to measure in subgroup analysis:

Dimension   

Example 
  Input conditions Performance in daytime vs nighttime images
Class distribution   Performance on majority class vs minority class
Demographic groups Performance across age groups, if applicable
Operating environments  Performance in different geographic regions
Sensor types Performance on different camera hardware

Process: 

  • Define the subgroups relevant to your deployment context 
  • Evaluate accuracy, precision, recall, and F1 separately for each subgroup 
  • Compute performance disparity between subgroups 
  • Flag subgroups with accuracy signi cantly below the global average 
  • Investigate root cause — is it data imbalance? Underrepresentation? Label noise? 

Performance disparity metric:

Disparity = max(subgroup accuracy) − min(subgroup accuracy) 

A large disparity indicates the model is not performing equitably.

4. Sources of Bias

Bias in AI models often arises not from malicious intent but from structural issues in data collection and curation.

Source    

Mechanism  

Example 
 Data imbalance  Model learns to favor majority class 80% class A, 20% class B → model biased toward A
Underrepresentation  Certain groups poorly represented    in training data  Model less accurate on groups it rarely     saw

Key implication for testing: Bias testing must happen before deployment. Once a biased model is in production, it has already affected real people. 

5. Fairness Metrics

There is no single universally agreed de nition of fairness. Different metrics capture different fairness properties. 

Metric     

Definition   

When to Use  
 Demographic Parity  Prediction rates equal across groups  When historical biases must be corrected
Equalized Odds   Equal TPR and FPR across groups   When both false positives and false   negatives have consequences 
Equal Opportunity  Equal true positive rate (recall) across groups   When false negatives are most harmful 
Individual Fairness  Similar individuals receive similar predictions   When fairness is de ned at the individual level 
Calibration Predicted probabilities correct across groups  When con dence scores drive downstream decisions 

Important: These metrics can conflict with each other and with overall accuracy. There is no single fairness metric that satis es all definitions simultaneously — this is a mathematical result known as the impossibility theorem in algorithmic fairness.

Fairness evaluation frameworks can compare performance across subgroups, measure statistical parity and highlight performance disparities. These tools do not automatically x bias — but they make it visible. Visibility is the first step toward correction.

6. Ethical Testing

Ethical testing means proactively asking whether a system could cause unintended harm, even when it is technically correct. 

Questions ethical testing must address:

  • Could this model's errors cause physical harm? (medical, autonomous driving)
  • Could this model reinforce existing social inequalities?
  • Could this model be used in ways not intended at deployment? (surveillance, tracking)
  • Are the errors symmetric — or do they systematically hurt speci c groups more?
  • What are the downstream consequences of a false positive vs a false negative?

Technical Correctness does not Guarantee Ethical Correctness.

A defect detection model that falsely rejects 30% of one manufacturing line but only 5% of another — at identical overall accuracy — causes economic harm to one production team. A surveillance model that correctly identi es threats 95% of the time still has privacy implications for the 100% of people it monitors. 

Engineers must think beyond technical metrics.

PART G: GLOSSARY

Term 

Definition  
  Inference Latency  Time from receiving input to returning a prediction
P50 / P95 / P99  The latency values below which 50%, 95%, 99% of requests fall
Throughput  Number of predictions processed per unit of time
Batch Size  Number of inputs processed simultaneously in one forward pass
Scalability Testing  Evaluating system behaviour under increasing concurrent load
Memory Leak  A defect where memory usage grows unboundedly over time
Quantisation  Reducing model weight precision (e.g., FP32 → INT8) to improve   speed and reduce size
Dynamic Quantisation  Post-training quantisation applied at inference time, targeting Linear   layers
SLA  Service Level Agreement — a performance commitment, e.g., P99 <   200ms
Warmup  Discarded initial inference runs that remove cold-start bias from   measurements
Adversarial Attack  Intentional, imperceptible input modification to cause model   misclassification
Model Inversion  Attack that reconstructs training data by analysing model outputs
API Abuse  Misuse of an API through flooding, extraction, or unauthorised   access
JWT  JSON Web Token — signed token for stateless authentication
Rate Limiting  Restricting requests per client within a time window
Sliding Window  Rate limiting algorithm that tracks request timestamps over a rolling   period
Defense in Depth  Applying multiple independent security controls simultaneously
Regression Testing  Verifying that new changes do not break previously working behavior
Quality Gate  Minimum criteria that must pass before code can proceed to   deployment
CI/CD  Continuous Integration/Delivery — automated testing on every code   change
Threshold-based Testing  ML testing where assertions check bounded behavior, not exact   outputs
pytest  Python testing framework that auto-discovers and runs test   functions
AAA Pattern  Arrange-Act-Assert — standard structure for a unit test
Fairness  Ensuring a model does not systematically disadvantage any group or   subgroup
Subgroup Analysis  Measuring model performance separately for different groups or   conditions
Demographic Parity  Equal prediction rates across demographic groups
Equalised Odds  Equal TPR and FPR across groups
Data Imbalance  Training data skewed toward certain classes or groups
Bias  Systematic error in model outputs that unfairly disadvantages   certain  groups
GDPR  General Data Protection Regulation — EU law governing personal   data processing
Data Minimisation  Principle of collecting only necessary data for a stated purpose
Right to Explanation  Requirement that automated decisions can be explained to affected   individuals
Ethical Testing  Proactive evaluation of whether a system could cause unintended   harm
